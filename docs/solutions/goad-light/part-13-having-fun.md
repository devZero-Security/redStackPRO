## These techniques need a victim - and that victim is *you*

Everything in this part is **passive / opportunistic**: you set a trap, but
nothing fires until a logged-in user does something ordinary (browses a share,
has an active session). The plant is under your control; the payoff waits on
someone else acting. On a real network there are always users - that is why
these work. Our cloud range is **headless**, so there is no automatic victim.

**So the solution operator plays the victim: RDP into the target host as the
victim user and manually detonate the trap**, while the attacker side (a
Responder / ntlmrelayx listener on the jumpbox foothold) is running. This is
exactly how mayfly does it ("simulate the victim with an RDP session"). See
[Manual detonation](#manual-detonation---you-play-the-victim) below.

> Alternative to a human: run a GOAD-style victim-simulation bot (scripted logins
> / share visits) so the traps fire on their own.

## Manual detonation - you play the victim

You reach the private Windows hosts through the jumpbox. Two ways, pick either:

- **Guacamole (easiest):** open the jumpbox's **Guacamole** console in the
  browser (it holds the range's public access and brokers RDP into the private
  hosts), open an **RDP connection to the target box**, and **log in as the
  specific victim user** with that user's domain credentials.
- **SSH tunnel:** forward the target's 3389 through the hodor foothold, then RDP
  to localhost as the victim:

  ```bash
  ssh -i <key> -L 3389:<target-ip>:3389 hodor@<jumpbox>   # then RDP 127.0.0.1 as e.g. north\catelyn.stark
  ```

Either way you end up logged in **as the specific victim user** (e.g.
`north\catelyn.stark`, `essos\daenerys.targaryen`) - that live session is what
springs the trap. Start the attacker-side listener on the jumpbox foothold
**before** detonating (e.g. `responder` for capture, or `ntlmrelayx` to relay to
an unsigned host).

Per technique - the operator logs in as the **victim**, performs the trigger, and
the **attacker** collects:

| Technique | Log in (RDP) as victim | Detonate (victim action) | Attacker collects |
|-----------|------------------------|--------------------------|-------------------|
| Coerce file (.url/.lnk/.scf) | e.g. `north\catelyn.stark` on winterfell | open `\\castelblack\all` in Explorer | victim's NetNTLMv2 on Responder → crack or relay |
| WebDAV coerce | `essos\khal.drogo` on braavos | browse `\\castelblack\all` (starts WebClient), then attacker runs PetitPotam over HTTP | HTTP auth → relay to LDAP (shadow creds / RBCD) |
| Token impersonation | a privileged user (RDP onto the host you own, e.g. castelblack - where you have SYSTEM from part 8) | just be logged on | steal their token (SharpImpersonate / execute-assembly) → act as them |
| RDP session hijack | victim `essos\daenerys.targaryen` on braavos (2016); attacker `essos\khal.drogo` on braavos | victim keeps a session open | attacker → SYSTEM (`PsExec -s`) → `tscon <id> /dest:<own-session>` takes it over |

> This is the intended flow for a headless lab: the reader **is** the victim.
> Two sessions (attacker + victim) make the cause/effect obvious. Server 2019
> (sevenkingdoms/north members) blocks RDP-session hijack; use the 2016 essos
> hosts for that one.
